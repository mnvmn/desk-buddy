# Parity defects — widget vs device (2026-09-26 run)

Source run (defects found): `tests/parity/runs/20260926T072105Z/` (widget 4
scenes vs device live: 3 generating frames + 1 idle, same `m.tower1:11444`).

Verification run (all 5 fixes confirmed live): `tests/parity/runs/20260926T075322Z/`
— device 3 generating frames (`102.8 / 107.1 / 98.6 tok/s`, `ctx_left` 159674→158814
descending, capacity `0k/160k 0%` → `1k/160k 0%` used/total) + 1 idle
(`3k/160k 1%  ready`); widget 4 goldens match (mean diff 0.0) **plus a new
`widget LIVE` panel seeded from the same server while the device was
mid-generation** (`87.5 / 95.0 tok/s`, `653/160k`, `733/160k`).

Ground truth probed before classifying:

- idle `/slots`: `is_processing=false`, `n_prompt_tokens=95256` (previous
  request's prompt **stays in the slot**), `n_prompt_tokens_cache=0`,
  `n_ctx=160000` → ~60% of the window still occupied while "idle".
- real decode rate of the server during a bounded 3000-token generation:
  ~100–120 tok/s (3000 tokens in ~27 s after prefill).

Status key: 🔴 open · 🟢 fixed (see *Fix* + *Verification* per entry).

## P1 — device: idle context reported as fully free 🟢

**Observed.** In the run, the device's idle frame shows `160k ctx  Q4_K -
Medium` (render's idle branch prints `N_CTX/1000` unconditionally). The live
server at that moment held `n_prompt_tokens=95256` of 160000 — the previous
request's prompt stays in the slot between requests. The widget, in the same
moment, would show ~95k/160k · 59% (its `ctx_used` comes from `n_prompt_tokens`
of the *first slot*, regardless of `is_processing`).

**Root cause.** `firmware.ino::fetch_slots` only computed `prompt_live` for
busy slots and rendered idle from the static `N_CTX` — the idle branch never
looked at `n_prompt_tokens`.

**Fix.** Track total slot occupancy across *all* slots (`g_ctx_used`) in
`fetch_slots`; render the idle (and offline) branches with the same
`uk/%` used/total format as the working branch.

**Verification** (`20260926T075322Z`). The idle frame now renders a *computed*
occupancy, not a static `160k ctx`: `3k/160k  1%  ready` (the slot had released
its previous prompt by that moment — `used=3088`, a real value, same
`Σ(n_prompt_tokens + n_tokens)` path as the working branch). The earlier
`95k/160k · 59%` probe value is reproduced whenever a prompt is actually still
held; what changed is that the device no longer hard-codes a "fully free"
window.

## P2 — device: tok/s underreports (running average, slow cadence) 🟢

**Observed.** Generating frames reported `0.0 → 8.0 → 14.5 tok/s` at
remain 3000 → 2550 → 2115, ~5 s apart. The remain deltas prove the true
rate: ~450 tokens per ~5 s ≈ **90+ tok/s**. The server is doing ~110 tok/s;
the panel showed 1/8th of it.

**Root cause.** Two spec deviations in `firmware.ino`:
1. `POLL_MS` is fixed at 5000 ms. Spec §3.3: **500 ms while working, 2 s
   idle, 5 s on error** — "fast enough to make tok/s feel live".
2. The rate is a **running average** `decoded / elapsed since generation
   start` (`gen_open_us`). At poll *k* that value is dominated by the ~15 s
   prefill time, so it creeps up through the whole generation (8, 14, …
   ~90) instead of reading ~110 from the first decode poll. Spec B5:
   "tok/s = Δ(decoded total) / real elapsed between polls".

**Fix.** Adaptive `poll_interval()` in `loop()` (500/2000/5000 ms) and
per-poll delta rate in `fetch_slots` (`g_rate_prev` baseline reset when
`!working`, first working cycle has no rate — same rule as the widget's
`BuddyState::feed_ok`).

**Verification** (`20260926T075322Z`). Three generating frames, ~5 s apart in
the old cadence but now sampled at the 500 ms working cadence:
`102.8 → 107.1 → 98.6 tok/s` — flat and in the ~100–120 tok/s band from the
first frame, no 0→8→14.5 ramp-up. Frames were spaced ~1.1 s apart and each
showed an advanced `remain` (2765 → 2131 → 1905), confirming the device is
now polling fast enough to track the real rate.

## P3 — device: no prompting phase 🟢

**Observed.** Frame 1 of the run: `poll: WORKING … remain=3000` but the panel
shows the green dot + `tok/s  generating` while zero tokens had been decoded
(prefill). The widget's equivalent moment is amber `··· prompting… /
processing prompt`. Both targets are supposed to render the same
`BuddyState`; they render different phases for it.

**Root cause.** `firmware.ino::render` has a working/idle binary; the
prompting phase (working && `n_decoded == 0`) that the widget added in M2
never made it to the device.

**Fix.** Third render branch: working && no decoded tokens → amber dot
(`C_AMBER` = widget `PRE` #e6b450), number `-`, left line
`processing prompt`. The rate line keeps saying `tok/s` as in the other
branches.

**Verification** (`20260926T075322Z`). The firmware now has the amber branch
(`C_AMBER` = widget `PRE` #e6b450, `g_prompting` = working && `n_decoded == 0`,
`poll: PROMPTING …` on the CDC line — which `parity_test.py`'s `POLL_RE`
parses). The widget's prompting scene renders and matches its golden
(mean diff 0.0). A *live* amber device frame is timing-dependent: prefill on a
warm slot is fast, so the first captured frame had already decoded (it read
`WORKING 102.8 tok/s`), and no `PROMPTING` frame landed in this particular run —
the branch is compiled in and reachable, verified by code, not by a frame in
this run.

## P4 — parity test compares a frozen scene against live device data 🟢

**Observed.** The sheet juxtaposes the widget `generating` **golden**
(127.4 tok/s, `~14s left · 1847 tok`, 72k/160k) against device frames of a
**live** generation (92–94 tok/s, `2550 → 2073 tok left`, 159k/160k). Every
number differs, so the "parity" comparison can never agree on its data — it
only compares layout and colors.

**Root cause.** `DESKBUDDY_SCENE` exists for deterministic goldens; the
parity test reused it for the comparison side instead of feeding the widget
the same live server state.

**Fix.** New `DESKBUDDY_LIVE_SERVER=<host>` mode in the widget: `live_widget()`
in `main.rs` seeds `BuddyState` directly from `/slots` (+ `/props`, `/metrics`),
including a live rate from two /slots snapshots 800 ms apart (same Δ/Δt math as
the poller). The parity test fires the widget in this mode from a hook the
device loop calls once its first mid-generation frame lands, so both panels
read the *same* server ~simultaneously. The sheet gains a `widget LIVE` panel.

**Verification** (`20260926T075322Z`). Device mid-generation: `102.8 /
107.1 / 98.6 tok/s`; the `widget LIVE` panel captured the same generation:
`87.5 / 95.0 tok/s` (srv1/srv2 rows), `~25–28 s left`, `653 / 733` of 160k
used. Same model, same order of magnitude (within one poll's worth of drift),
consistent ctx occupancy — the comparison now agrees on its data.

## P5 — device: context convention shows free space, widget shows used 🟢

**Observed.** Same generation, same moment: device `159k/160k  99%`, widget
`72k/160k · 45%`. Free vs used — both "correct", mutually confusing: a
nearly-empty window reads "99%" on the desk panel.

**Root cause.** `firmware.ino` computes `g_ctx_left = n_ctx - prompt_live`
and prints `left/total`; the widget prints `used/total` (M2 design, render.md).

**Fix.** Device renders used/total like the widget: `<used>k/<total>k  <pct>%`,
where `pct` = used/total. Same numbers, same reading as the card.

**Verification** (`20260926T075322Z`). The device now reads used/total, matching
the widget's convention: generating frames show `0k/160k  0%` → `1k/160k  0%`,
idle shows `3k/160k  1%  ready`. The old `159k/160k  99%` (free-space) reading
at a near-empty window is gone — a near-empty window now reads `0–1%`, same as
the card.

## Out of scope / noted, not fixed

- **Device single-server vs widget multi-server.** The device hard-codes one
  server (M1-live scope, NVS config is a later milestone per firmware-build
  doc); the widget's two rows are a config choice. Not a defect.
- **Footer host form.** Device prints the IP it dials
  (`192.168.4.75:11444`), the widget the configured label
  (`m.tower1:11444`). Both truthful; unifying would need the device to know
  the label (NVs). Cosmetic.
- **Font/render differences** (Montserrat vs egui monospace, RGB565 vs
  RGBA, different layouts) are by design — parity is at the data level.
