# Module: `scene` — plumber picture, follows live state (device)

> **Status: implemented** (M3 screensaver, reached by touch). Four
> pre-rendered pictures, generated by
> [`shared/scene-assets/render_scene.py`](../../../shared/scene-assets/README.md)
> into `plumber_scene.h`, baked into flash for the 480×480 AMOLED. The
> bitmaps live in `shared/scene-assets/` (single source of truth for BOTH
> targets — the widget blits the same scene, see
> [widget scene design](../../widget/modules/scene-design.md)).

**The picture tracks the live server state** — it is the device twin of the
widget's `BuddyState::phase()`. A poll re-derives the phase (worst network
first) and, while the scene screen is open, swaps the bitmap to match.
**The scene is the device's default screen** (boot lands on it); tapping
only toggles scene ↔ card, it does not cycle pictures. The four pictures:

| picture | content |
|---|---|
| **working**   | `Phase::Generating` — sprinting plumber on the ground, no coins |
| **prompting** | **same picture as `working`** (reused; no distinct art) |
| **idle**      | `Phase::Idle` — the calm level itself, **scene only (no plumber)** |
| **down**      | calm level + a **Piranha Plant in the middle of the scene** |

The character appears while a server is busy (working/prompting); down shows
the Piranha Plant instead; idle is scenery only. (The old standalone **night** picture
has been removed entirely.)

## How it's built

- **Pre-rendered bitmaps, not live-drawn.** `shared/scene-assets/render_scene.py`
  rasterises all four states at **6 px/cell**: the 80×80 grid is **480×480,
  full-bleed** — the whole square panel is scene (sky at the top, ground at
  the bottom; the black `C_PANE` background is only the margin around the
  data card, not a letterbox for the scene).
  Output: `plumber_scene.h` with four `const uint8_t[460800]` arrays
  (480·480·2 RGB565 each, little-endian = `lv_color_t` order).
- **Flash, not RAM.** The C6 has no PSRAM, so the arrays live in `rodata`
  (~1.8 MB total). They are referenced by four `lv_image_dsc_t`
  (`LV_COLOR_FORMAT_RGB565`) and shown through a normal `lv_image` — LVGL
  *streams* the pixels from flash, so this adds **no heap**. The pictures
  overflow the stock 3 MB app partition, so the device is built and flashed
  with the custom `app4M_fat8M_16MB` partition scheme (4 MB app ×2 /
  8 MB FAT; see the FQBN in the desk-buddy-scenes skill).
- **Full canvas, centered for safety.** `build_scene()` puts the `lv_image`
  on its own screen (black `C_PANE` bg) with `lv_obj_align(LV_ALIGN_CENTER)`;
  the LVGL canvas is the full 480×480 panel, so the picture covers every
  pixel and the alignment is a no-op (it guards against size drift).
- **Same orientation as the card.** The card is authored in LVGL logical
  coordinates and the panel flush rotates every tile 90° CW
  (`px=H-1-ly, py=lx`). The scene image is drawn at identity in that *same*
  coordinate frame, so the flush rotates it identically — it reads in the same
  orientation convention as the card (the confirmed-correct baseline). Do **not**
  pre-rotate the frames: that would offset the scene an extra 90° from the card.

## Touch

Taps are full-screen `LV_EVENT_CLICKED` catchers (an invisible,
`remove_style_all`'d object sized to the panel, created last so it sits on
top). One on the scene goes back to the card; one on the card re-opens the
scene showing the **currently derived** picture. The scene is also the boot
(default) screen — `setup()` loads it after building both screens. This uses
LVGL's pointer indev (CST9220) directly — no custom tap state machine, so it
works regardless of which screen is active.

> The spec's **KEY button** (M3) is still the unverified GPIO; touch is the
> working input. See [button.md](button.md).

## Verification (no physical tapping)

The SH8601 panel is write-only, so the only trustworthy render channel is the
LVGL draw buffers (see [display-bsp.md](display-bsp.md)). Serial commands
drive the same code paths a tap uses, then `CAP` streams the framebuffer:

- `SOP` → open the scene exactly like a card tap
- `SCN` → working · `SCP` → prompting · `SCI` → idle · `SDN` → down ·
  `CAR` → card · `CAP` → screenshot

The picture commands are **manual overrides**: each opens the scene if it's
closed and **holds** its picture — the live re-derivation is suspended while
an override is set, so the panel can't fight the command back to IDLE. The
override clears when the scene closes (tap/`CAR`), when the card is shown,
or on `SOP`. This is still
the normal path — a live generation drives the panel `IDLE → WORKING → IDLE`
on its own, and that was verified end-to-end (start a 900-token completion,
watch the `scene:` lines, CAP the panel at each state).
`python tools/capture_scene.py COM3 out` still walks all five views
(working / prompting / idle / down / card) for a full-coverage contact sheet.
